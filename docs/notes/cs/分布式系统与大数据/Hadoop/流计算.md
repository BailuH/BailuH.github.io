## 一、流计算概述

### 1.1 静态数据与流数据

| 维度 | 静态数据 | 流数据 |
|------|---------|--------|
| **定义** | 历史数据的快照，存储在数据仓库中 | 大量、快速、时变的动态数据集合，持续到达 |
| **实例** | 数据仓库中的历史销售记录 | PM2.5检测数据、电商用户点击流 |
| **处理模式** | 批量计算（Batch Processing） | 实时计算（Real-time Processing） |
| **时效性** | 旧数据，某一时刻的快照 | 实时产生，价值随时间流逝而降低 |

**流数据的核心特征（重要）：**
- 数据快速持续到达，潜在数据量无穷无尽
- 数据来源众多，格式复杂
- 数据量大，但不十分关注持久化存储（处理后即丢弃或归档）
- 注重数据的整体价值，不过分关注个别数据
- 数据顺序可能颠倒或不完整，系统无法控制新到达元素的顺序

### 1.2 批量计算与实时计算

**批量计算（Batch Computing）：**
- 面向静态数据，有充裕时间进行处理
- 典型代表：Hadoop生态系统（HDFS、HBase、MapReduce）
- 关注**吞吐率**

**实时计算（Real-time Computing）：**
- 面向流数据，必须在数据到达时立即处理
- 响应时间要求：**秒级甚至毫秒级**
- 关注**延迟**
- 流计算即针对流数据的实时计算

![image.png](https://bailu-1382509292.cos.ap-beijing.myqcloud.com/obsidian/20260604081848477.png)

### 1.3 流计算的概念

> **流计算**：实时获取来自不同数据源的海量数据，经过实时分析处理，获得有价值的信息。

**核心理念**：数据的价值随着时间的流逝而降低。因此，当事件出现时就应该立即处理，而不是缓存起来批量处理。

**流计算系统的六大需求：**

| 需求 | 说明 |
|------|------|
| **高性能** | 每秒处理几十万条数据 |
| **海量式** | 支持TB级甚至PB级数据规模 |
| **实时性** | 延迟达到秒级甚至毫秒级 |
| **分布式** | 支持平滑扩展 |
| **易用性** | 快速开发和部署 |
| **可靠性** | 可靠地处理流数据 |

### 1.4 流计算与 Hadoop

**为什么 Hadoop 不适合流计算？**

- Hadoop 设计初衷是面向大规模数据的**批量处理**
- MapReduce 内部机制（如任务启动、中间结果落盘、作业调度）均为批处理高度优化
- 即使将批量处理改为"小批量处理"（将输入数据切成小片段，周期性启动 MapReduce 作业），仍存在以下问题：
  1. 切分增加了额外开销
  2. 需要处理片段之间的依赖关系
  3. 需要改造 MapReduce 以支持流式处理

> **结论**：Hadoop 擅长静态数据批处理，不适合流计算（鱼和熊掌不可兼得）。

### 1.5 流计算框架分类

| 类型 | 代表产品 | 说明 |
|------|---------|------|
| **商业级** | IBM InfoSphere Streams、IBM StreamBase | 企业级解决方案 |
| **开源框架** | Twitter Storm、Yahoo! S4 | 社区驱动，广泛应用 |
| **公司自研** | 百度 Dstream、淘宝银河流数据处理平台、Super Mario | 支撑自身业务需求 |

## 二、流计算处理流程

流计算处理流程包含**三个阶段**：数据==实时==采集 → 数据==实时==计算 → ==实时==查询服务。

### 2.1 传统数据处理流程 vs 流处理流程

| 对比维度     | 传统数据处理流程   | 流处理流程       |
| -------- | ---------- | ----------- |
| **数据性质** | 预先存储好的静态数据 | 实时到达的动态数据   |
| **用户行为** | 用户主动发出查询   | 系统主动推送实时结果  |
| **结果时效** | 过去某一时刻的结果  | 实时结果        |
| **存储前提** | 数据必须先存储再处理 | 数据可不存储，直接处理 |

**传统流程的隐含前提：**
1. 存储的数据是旧的（过去某一时刻的快照，查询时已不具备时效性）
2. 需要用户主动发出查询来获取结果

### 2.2 数据实时采集

**目标**：实时汇总来自不同机器、不同数据源的海量数据，保证实时性、低延迟与稳定可靠。

**典型开源采集系统：**
- LinkedIn **Kafka**
- 淘宝 **Time Tunnel**
- 基于 Hadoop 的 **Chukwa** 和 **Flume**

**数据采集系统的三层架构（高度抽象的模型）：**

| 组件            |                  功能                   |
| ------------- | :-----------------------------------: |
| **Agent**     |         主动采集数据，推送到 Collector          |
| **Collector** |      接收多个 Agent 的数据，有序、可靠、高性能地转发      |
| **Store**     | 存储 Collector 转发的数据（流计算场景下通常不存储或仅短暂缓存） |

### 2.3 数据实时计算

- 对采集的数据进行**实时分析和计算**
- 处理后的数据可视情况：
  - **存储**：以便后续离线分析
  - **直接丢弃**：在时效性要求极高的场景下

### 2.4 实时查询服务

- 将流计算框架得出的结果供用户**实时查询、展示或存储**
- 系统**主动推送**实时结果给用户，无需用户主动查询
- 与传统定时查询的本质区别：传统方式获取的结果仍是基于过去某一时刻的数据

## 三、流计算的应用

### 3.1 实时分析

**典型场景**：电商促销活动（如淘宝"双十一"）中的广告效果分析。

- **传统方式**：分布式离线计算，延时几小时甚至一天，隔天才能得到结果，对仅持续一天的促销活动失去价值
- **流计算方式**：秒级响应，商家可根据广告效果即时调整投放策略

**案例**：淘宝"量子恒道"开发的 **Super Mario** 框架
- 处理每天 **TB 级**实时流数据
- 从用户请求到数据展示，延时控制在 **2-3 秒**
- 特点：毫秒级、低延迟、高可靠性

### 3.2 实时交通

- **传统导航**：使用历史交通数据或静态路况信息
- **流计算导航**：获取海量实时交通数据并进行实时分析，在行驶过程中根据交通状况变化**实时更新路线**，始终提供最佳行驶路线

### 3.3 适用场景判断

**适合流计算的场景：**
- 需要处理持续到达的流数据
- 对数据处理有较高实时性要求（秒级/毫秒级）

**不适合的场景：**
- 对历史数据的深度离线挖掘
- 对时效性无要求的批量分析

## 四、开源流计算框架 —— Storm

### 4.1 Storm 简介

- **Twitter** 开发的免费、开源分布式实时计算系统
- Storm 对于实时计算的意义，**类似于 Hadoop 对于批处理的意义**
- 可简单、高效、可靠地处理流数据，支持多种编程语言
- 可方便地与数据库系统整合，开发强大的实时计算系统

**Twitter 的分层数据处理架构（Lambda 架构思想）：**
- 批处理视图（Batch View）+ 实时视图（Real-time View）
- 查询时合并两个视图的结果，批处理系统后续修正实时视图

### 4.2 Storm 的特点

| 特点 | 说明 |
|------|------|
| **整合性** | 方便与队列系统和数据库系统整合 |
| **简易的 API** | 使用简单方便 |
| **可扩展性** | 并行特性，可运行在分布式集群中 |
| **容错性** | 自动进行故障节点重启、任务重新分配 |
| **可靠的消息处理** | 保证每个消息都能完整处理 |
| **多语言支持** | 支持各种编程语言定义任务 |
| **快速部署** | 快速部署和使用 |
| **开源免费** | 开源框架 |

### 4.3 Storm 设计思想

Storm 的核心术语：

#### （1）Streams（流）
- 将流数据描述为一个无限的 *Tuple（元组）序列*
- 以分布式方式并行创建和处理
- 每个 *Tuple* 是一组值（*Value List*），按预定义字段顺序填入

#### （2）Spout（数据源）
- 每个 *Stream* 的源头，抽象为 _Spout_
- 从外部数据源（队列、数据库等）读取数据，封装成 _Tuple_ 发送到 _Stream_
- **主动角色**：接口内有 `nextTuple()` 函数，_Storm_ 框架不停调用该函数

#### （3）Bolt（处理单元）
- 将 _Streams_ 的状态转换过程抽象为 _Bolt_
- 可执行过滤、函数操作、Join、数据库操作等
- 处理后的 _Tuple_ 可作为新的 _Streams_ 发送给其他 _Bolt_
- **被动角色**：接口有 `execute(Tuple input)` 方法，接收到消息后调用

#### （4）Topology（拓扑）
- 由 _Spouts_ 和 _Bolts_ 组成的网络，抽象为 _Topology_
- 可视为**流转换图**：节点是 _Spout_ 或 _Bolt_，边表示数据流动方向
- 每个组件都是**并行运行**的，可指定并行度
- _Topology_ 定义是 _Thrift_ 结构体，支持各种编程语言

#### （5）Stream Groupings（流分组）
决定 Tuple 在两个组件间（Spout→Bolt 或 Bolt→Bolt）的传送方式：

| 分组方式 | 说明 |
|---------|------|
| **ShuffleGrouping** | 随机分组，保证每个 Bolt Task 接收数量大致一致 |
| **FieldsGrouping** | 按字段分组，相同字段的 Tuple 分配到同一 Task |
| **AllGrouping** | 广播发送，每个 Task 都收到所有 Tuple |
| **GlobalGrouping** | 全局分组，所有 Tuple 发送到同一个 Task |
| **NonGrouping** | 不分组，与 ShuffleGrouping 类似，但同线程执行 |
| **DirectGrouping** | 直接分组，直接指定某个 Task 处理 |

### 4.4 Storm 框架设计

#### Storm vs Hadoop 架构对比

| 维度 | Hadoop | Storm |
|------|--------|-------|
| **应用名称** | Job | Topology |
| **系统角色（Master）** | JobTracker | Nimbus |
| **系统角色（Worker）** | TaskTracker | Supervisor |
| **组件接口** | Map / Reduce | Spout / Bolt |

**核心区别**：MapReduce 作业最终会完成并结束；Topology **持续处理消息**，直到人为终止。

#### Storm 集群架构（Master-Worker）

| 节点类型 | 后台程序 | 职责 |
|---------|---------|------|
| **Master 节点** | **Nimbus** | 集群范围内分发代码、为 Worker 分配任务、监测故障（类似 JobTracker） |
| **Worker 节点** | **Supervisor** | 监听分配给本机的工作，根据 Nimbus 指令启动/停止 Worker 进程 |

**协调组件：ZooKeeper**
- 负责 Nimbus 与多个 Supervisor 之间的所有协调工作
- 若 Nimbus 或 Supervisor 意外终止，重启时可读取、恢复之前状态，保证 Storm 极其稳定

#### Storm 工作流程

1. 客户端提交 Topology 任务到 Storm 集群
2. Nimbus 将分配任务写入 **ZooKeeper**
3. Supervisor 从 ZooKeeper 获取分配的任务，启动 **Worker 进程**
4. Worker 进程执行具体任务

## 五、Spark Streaming

### 5.1 Spark Streaming 设计

**数据源整合**：可整合 Kafka、Flume、HDFS、普通 TCP 套接字等多种输入数据源。

**核心原理**：
- 将实时输入数据流以**时间片（秒级）**为单位进行拆分
- 经 Spark 引擎以**类似批处理**的方式处理每个时间片数据

**核心抽象：DStream（Discretized Stream，离散化数据流）**
- 表示连续不断的数据流
- 内部实现：输入数据按时间片（如 1 秒）分成一段一段的 DStream
- 每一段数据转换为 Spark 中的 **RDD**
- 对 DStream 的操作最终转变为对相应 **RDD** 的操作

### 5.2 Spark Streaming vs Storm 对比

| 对比维度 | Spark Streaming | Storm |
|---------|----------------|-------|
| **延迟级别** | 无法实现毫秒级（100ms+） | **可实现毫秒级响应** |
| **执行引擎** | 构建在 Spark 上，低延迟执行引擎 | 纯实时流处理引擎 |
| **容错处理** | RDD 数据集更容易做高效容错处理 | 需额外机制保证容错 |
| **处理模式** | **小批量处理**（Micro-batch） | 逐条处理（True Streaming） |
| **编程模型** | 可兼容批量和实时数据处理逻辑 | 纯流处理 |
| **生态整合** | 可与 Spark SQL、MLlib、GraphX 统一部署 | 主要专注于流处理 |
| **编程语言** | 主要支持 Scala/Java/Python | 通过 Thrift 支持任何编程语言 |

### 5.3 应用场景选择

| 场景需求 | 推荐框架 | 理由 |
|---------|---------|------|
| 需要**毫秒级**响应 | **Storm** | Spark Streaming 无法达到毫秒级 |
| 需要**编程灵活性**、多语言支持 | **Storm** | 使用 Apache Thrift，可用任何语言编写 Topology |
| 需要**流计算 + 图计算/机器学习/SQL** 结合 | **Spark Streaming** | Spark 生态可统一部署各组件，提供一体化编程模型 |
| 需要**历史数据 + 实时数据联合分析** | **Spark Streaming** | 小批量处理方式兼容批量和实时逻辑 |

## 六、本章小结

1. **流数据**是持续到达的大量动态数据，其价值随时间流逝而降低，处理强调**实时性**（秒级/毫秒级）。
2. **Hadoop/MapReduce** 面向静态数据批量处理，不适合持续到达的流数据。
3. 流计算处理流程包括：**数据实时采集**（Kafka/Flume 等）→ **数据实时计算** → **实时查询服务**（主动推送）。
4. **Storm** 是经典的纯实时流计算框架，核心概念为 Spout、Bolt、Topology，通过 ZooKeeper 协调，可实现毫秒级响应。
5. **Spark Streaming** 基于微批处理（DStream → RDD），延迟在 100ms 以上，但可与 Spark 生态无缝整合，适合需要批量与实时结合分析的场景。

---

> **关键记忆点**：批处理关注**吞吐率**，流处理关注**延迟**；Hadoop 是批处理的代表，Storm 是纯流处理的代表，Spark Streaming 是微批处理的代表。
